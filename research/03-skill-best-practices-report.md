## Part 1 — Researched best practices (with URLs)

### 1.1 Tool/function descriptions for LLMs

**Anthropic — "Writing effective tools for agents"** (https://www.anthropic.com/engineering/writing-tools-for-agents) is the canonical reference. Key rules that apply directly here:
- A tool description should state **what the tool does**, **when to use it**, and — critically — **when NOT to use it and what to use instead** (this is what makes tool selection reliable).
- **Include concrete examples** in descriptions; models pattern-match on real-looking JSON, not on abstract prose.
- Describe **edge cases, failure modes, and defaults** so the model can self-correct.
- Keep input schemas **small and flat**: only parameters the model actually needs; avoid nesting and `$ref`/`$defs` indirection; use `enum` + `default` where values are bounded; **every parameter gets a `description`**.
- Test tools with the actual model; description quality is the single highest-leverage fix for tool-call accuracy.

**OpenAI function-calling guidance** (https://developers.openai.com/cookbook/examples/o-series/o3o4-mini_prompting_guide and community: https://community.openai.com/t/prompt-structure-put-detail-in-function-description-or-user-prompt/943912/5): put the detail **in the function/parameter descriptions**, not in the user prompt; write parameter descriptions that say what the value means, its units/format, and defaults; use `enum` to constrain choices; keep `required` minimal and truthful.

**MCP Specification — tool annotations & docs** (https://ibm.github.io/mcp-context-forge/1.0.x/using/tool-annotations/, https://developers.outreach.io/mcp-server/tool-annotations, https://github.com/modelcontextprotocol/modelcontextprotocol/issues/1382): the spec's `readOnlyHint`, `destructiveHint`, `idempotentHint`, `openWorldHint` give the model cheap semantic safety signals — this package already sets `ReadOnlyHint`/`DestructiveHint`/`IdempotentHint` on `[AiTool]`, but the SKILL.md bodies do not consistently surface the destructive/irreversible ones as prose warnings. **SEP-1382 "Documentation Best Practices for MCP Tools"** is the in-flight spec issue on exactly this topic (description formula, examples, schema hygiene).

**DeepSeek function calling** (https://api-docs.deepseek.com/guides/tool_calls/): DeepSeek models consume OpenAI-style tool schemas, but there is **concrete ecosystem evidence that DeepSeek handles `$ref`/`$defs` poorly** — e.g. opencode's "expand $ref/$defs for DeepSeek compatibility" (https://github.com/anomalyco/opencode/pull/32955) and vllm's "resolve $ref/$defs in tool schemas before type coercion" (https://app.semanticdiff.com/gh/vllm-project/vllm/pull/46925/overview). Implication: **inline/expand schemas for DeepSeek rather than relying on `$defs` references**; keep schemas token-lean since they are re-sent on every turn. SuperAgent's README documents that providers accept *different* JSON Schema subsets — Gemini rejects `$ref`/`$defs`/`oneOf` (https://github.com/ForgeOmni/SuperAgent).

**JSON Schema authoring for LLM tool calling** (https://github.com/agentpatterns-ai/website/blob/main/standards/tool-calling-schema-standards.md, https://raw.githubusercontent.com/kesslerio/attio-mcp-server/22f48b08b3c4a0b257f035460b1f51c6710aae83/docs/mcp-schema-guidelines.md): every property needs a description; avoid untyped/`any` properties (models guess and guess wrong); prefer `enum` over free strings; state defaults; avoid `additionalProperties: true` catch-alls; **tokens are a cost — duplicated `$defs` blocks are pure waste**.

**Quality rubric** (https://glama.ai/mcp/servers/7836246/claude-team-mcp/score): a top-rated tool description answers "when to use this tool, when not to, what alternatives exist" — a usable checklist line for every SKILL.md.

### 1.2 Skills: frontmatter = trigger, body = instructions

**Anthropic Agent Skills** (https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills; spec: https://mintlify.wiki/anthropics/skills/spec/metadata-schema, frontmatter: https://mintlify.wiki/anthropics/skills/creating-skills/frontmatter):
- A skill is a folder with `SKILL.md`: **YAML frontmatter (`name`, `description`)** + markdown body.
- The frontmatter `description` is the **selection trigger** — the model reads it to decide whether to load the skill, so it must be a compact "what + when (+ when not)" statement.
- The **body is loaded on demand** and holds full instructions: when to use, step-by-step procedure, **concrete examples**, edge cases, warnings.

**Claude Code skills** (https://code.claude.com/docs/en/skills): `name` + `description` required; description should be **concise** and say when to use the skill; body carries the how-to.

**Observed DeepSeek Harness behavior (this session):** the harness exposes each skill's frontmatter description in the session skill catalog and loads the full body only when the skill is invoked — confirming the "description = trigger, body = instructions" contract. Long or vague descriptions dilute the catalog; the body should not be needed to decide whether to call the tool.

**Skill-authoring checklists** worth mirroring: obra/superpowers "anthropic best practices" (https://github.com/obra/superpowers/blob/main/skills/writing-skills/anthropic-best-practices.md) and Jamie-BitFlight's authoring checklist (https://github.com/jamie-bitflight/claude_skills/blob/main/plugins/plugin-creator/skills/skill-creator/references/authoring-checklist.md).

### 1.3 Implications for this package (synthesis)

1. **Frontmatter description** = the tool's entire selection surface for the model → ≤2 sentences, formula: *What + when + when-not + key caveat*.
2. **Examples must be real JSON**, not `string_value` placeholders — every audit file fails this (see Part 2).
3. **Expand `$defs` inline for DeepSeek** — but deduplicate per-file; a 400-line SKILL.md (gameobject-find) is mostly repeated `ViewQuery`/`GameObjectRef`/`SerializedMember` blocks the model re-reads each time.
4. **Kill `any` types** in the input table — the schema already knows the real types; the table must agree.
5. **Safety prose** must appear in body *and* trigger: dirty-scene precondition (tests-run), OnEnable side effects (screenshot-isolated), irreversibility (gameobject-destroy, assets-delete), main-thread rules (unity-skill-create), AssetDatabase refresh after disk writes (script-*).
6. **Encoding**: non-ASCII characters are double-encoded in generated files (see Fix #1) — must be fixed at the writer, not per-attribute.

### Systemic issues (apply to nearly all 83 files)

- **S1 — Placeholder examples (ALL files):** every "Example input" JSON is `"param": "string_value"` (booleans/numbers/enums included). Zero real payloads anywhere. Produced by the base `SkillFileGenerator` example generator inside Feeder.McpPlugin.dll (Unity override only wraps it). Highest-leverage fix in the set.
- **S2 — Mojibake (76/83 files):** non-ASCII chars (`—`, `→`, `…`) are double-encoded (`â€”`) in generated files; clean C# source (`Assets.Delete.cs` line 31 is correct `—`) proves the **writer** double-encodes UTF-8. Bodies of nearly every skill are affected; frontmatter descriptions are ASCII-only so triggers survive, but the fix belongs in the file writer (write UTF-8 without re-encoding).
- **S3 — `any` types in input tables:** `gameObjectRef`, `assetRef`, `componentRef`, `paths`, `viewQuery`, `filter`(reflection), `parameters`(script-execute), all of gameobject-modify read as `any` while the schema `$defs` defines real shapes. The table actively lies; DeepSeek models will guess wrong shapes.
- **S4 — `$defs` bloat:** identical 30-line blocks (`ViewQuery`, `GameObjectRef`, `AssetObjectRef`, `SerializedMember`, `PathPatch`) repeat per file and twice per file (input + output). gameobject-find = 402 lines / 13.9 KB for a 7-param tool; scene-get-data = 420 lines. Token cost with near-zero information gain; DeepSeek benefits from inline schemas, but **once** per file.
- **S5 — Ambiguity between similar tools:** object-get-data vs assets-get-data vs gameobject-component-get vs scene-get-data all describe "get serialized data"; none cross-reference when to pick which (only "use gameobject-find first"). The `paths`/`viewQuery` boilerplate is copy-pasted, so nothing differentiates them.
- **S6 — Inconsistent defaults:** defaults live only in bodies (or not at all); the input table has no Default column; examples show `0`/`false` where defaults are documented (screenshot-camera `width: 0`).
- **S7 — Safety signal inconsistent:** good preconditions exist for tests-run/screenshot-isolated/scene-save, but destructive tools lack trigger-level "irreversible" warnings; main-thread/AssetDatabase-refresh guidance exists only inside unity-skill-create (correct place) yet generated bodies for script-* don't re-state the post-write refresh contract in a uniform way.
- **S8 — Duplication of the `[Description]` attribute:** bodies frequently restate the parameter-level `Description` text (script-execute, tests-run) — tokens spent twice.

## Part 3 — The authoring standard (ready to apply to `[AiSkillDescription]`/`[AiSkillBody]`)

### 3.1 Frontmatter description (`[AiSkillDescription]`) — the trigger

Formula (1–2 sentences, ≤ ~200 chars, aim ≤ 160):
`What it does + when to use + when NOT to use (or what to use instead) + the single most important caveat.`

Rules:
1. Start with a verb in present tense ("Finds…", "Modifies…", "Runs…").
2. Name the concrete inputs only if they're few and important (`openedSceneName`), otherwise say "see body".
3. Include a **negative clause** when siblings overlap: e.g. object-get-data: "for any UnityEngine.Object; for assets use assets-get-data, for scene roots use scene-get-data."
4. Surface hard preconditions inline: "every open scene must be saved" (tests-run), "irreversible — cannot be undone" (destroy/delete tools), "may fire OnEnable" (screenshot-isolated).
5. Never exceed ~2 sentences; the catalog lists ~80 skills — long triggers are noise.

### 3.2 Body (`[AiSkillBody]`) — the instructions

Fixed section order (markdown):
1. **1-paragraph summary** (what it returns and does) — may reuse the trigger but add output expectations ("Returns base64 PNG", "Returns `TestRunResponse` with Summary/Results/Logs").
2. **When to use / When not to use** (2 bullets each) — explicit alternatives: "Prefer gameobject-component-get over object-get-data for a component's fields."
3. **Inputs** — one bullet per param: name, type, **default**, semantics, units, constraints, mutual exclusions (`paths` vs `viewQuery`). A table is fine; a **Default column is mandatory**.
4. **Behavior / side effects** — what the tool mutates, refresh/domain-reload behavior, main-thread notes, undo status.
5. **Edge cases & failure modes** — what throws and why (the model self-corrects from these).
6. **Concrete example JSON** — REAL values, never `string_value`: e.g. `{"gameObjectRef": {"name": "Player"}, "includeComponents": true}` or `{"filter": "t:Material l:red"}`.
7. **Cross-references** — which skills to call before/after.
8. **Warnings box** — safety (see 3.4).

Token budget (DeepSeek fit): target **≤ 150 lines** per SKILL.md (bodies only); hard cap ~200. If a schema drags you over, cut the schema, not the prose.

### 3.3 JSON Schema policy

1. **Expand `$defs` inline** (DeepSeek compatibility, per opencode/vllm evidence) — but **include each shared type exactly once per file**; merge input+output into one schema section if the generator supports it, or emit output schema only when the shape is not obvious from the input table.
2. **Drop the Input JSON Schema when the input table fully documents the params** (or vice versa) — never both verbatim. Keep the schema where types are non-trivial (refs, nested patch objects).
3. **Never type a param `any`** in table or schema when a real type exists; for genuinely free-form params (`jsonPatch`, `lights`, `parameters`), provide a worked example instead of `additionalProperties: true`.
4. **Every property gets a description**; bounded values become `enum`; numeric params get `minimum`/`maximum` and units (screenshot-camera: pixels, 1…8192).
5. **Defaults** appear in the schema (`default: 10` for maxResults) — DeepSeek honors them.
6. **Output schemas**: keep only when the model must parse fields (structured results); a tool returning "no structured output" (scene-save) needs no schema at all — current files already do this correctly.

### 3.4 Unity safety-warning rules (must appear in body; trigger if severe)

- **Irreversible ops** (gameobject-destroy, assets-delete, script-delete, profiler-clear-data): "⚠ Irreversible — cannot be undone. Verify the target first (use X to inspect)."
- **Precondition ops**: tests-run → "dirty scenes abort"; script-update-or-create/package-* → "triggers domain reload; result delivered later via requestId".
- **Side-effect ops**: screenshot-isolated → OnEnable caveat + `isolated=false` escape hatch.
- **Editor-state ops**: editor-application-set-state → "throws if compilation errors exist; inspect state first".
- **Main thread**: any tool doing Unity API work states "runs on the main thread; do not expect threading behavior".
- **External file writes**: script-*/assets-* → "AssetDatabase.Refresh after write; wait for compilation".

### 3.5 Consistency & hygiene

- One canonical paragraph for `paths`/`viewQuery` (token-saving) — write it once and reference it: "see the shared 'Path-scoped reads' note" instead of copy-pasting 6 lines into 20 files.
- Consistent terminology: GameObject vs object vs asset vs scene-root — every "get data" tool states its scope in the first sentence.
- Keep the body's "Inputs" and the parameter `[Description]` attributes **non-duplicative**: put the full detail in one place (prefer the body; keep `[Description]` short for the MCP schema).
- Unicode: em dashes/arrows are fine in C# source but the **generator writer must write UTF-8 once** (fix S2) — after that, prefer plain ASCII punctuation in attribute strings to be safe.

## Part 4 — Top 10 prioritized fixes

1. **Fix the example-JSON generator (S1).** Replace the `string_value` placeholder emitter in the base `SkillFileGenerator` (Feeder.McpPlugin.dll) with type-aware samples: strings → realistic values ("Assets/Materials/Red.mat"), numbers → valid defaults, booleans → `true`/`false` properly, enums → first enum value, objects → `{"instanceID": 0}`-style refs. This single change upgrades all 83 files. *(Generator, not per-attribute.)*
2. **Fix UTF-8 double-encoding (S2).** In the skill file writer, write the markdown with a single `Encoding.UTF8` pass (no `Encoding.Default`/Latin-1 re-encode). Verify `—` survives. *(Generator.)*
3. **Eliminate `$defs` bloat (S4).** Emit each shared `$defs` type once per file (merge input+output schema sections), or drop the input schema when the table covers it. Target: gameobject-find ≤ 200 lines, scene-get-data ≤ 250. *(Generator + authoring rule.)*
4. **Kill `any` in the input table (S3).** The table's Type column must show the resolved type (`GameObjectRef`, `List<string>`, `ViewQuery`), never `any`, for every param. *(Generator: map schema `$ref` → human type name.)*
5. **Real examples for the highest-value tools.** Manually author concrete example payloads for: gameobject-modify (parallel-array shape), assets-modify (`pathPatches`/`jsonPatch` shapes), script-execute (a 3-line C# body), reflection-method-find (`MethodRef`), screenshot-isolated (a valid full call). These are the tools where DeepSeek currently guesses wrong. *(Attribute bodies.)*
6. **Add "when NOT to use / alternatives" to the data-getting family.** Distinguish object-get-data vs assets-get-data vs gameobject-component-get vs scene-get-data with explicit selection guidance in trigger + body. *(Attributes.)*
7. **Safety warnings in triggers for destructive tools (S7).** gameobject-destroy, assets-delete, script-delete, editor-application-set-state: add "Irreversible — cannot be undone" / "verify first" to `[AiSkillDescription]`, mirroring profiler-clear-data. *(Attributes.)*
8. **Enum + default hygiene (S6).** Ensure schema `enum` for every string choice (testMode, logType, backgroundMode, cameraView — screenshot files already have them) and `default:` values; fix examples that show `0` where defaults are documented (screenshot-camera width/height). *(Generator + attributes.)*
9. **Fix script-update-or-create contract inconsistency.** Body says `requestId` required; table/example omit it. Standardize the [RequestID] tools' docs to show the processing/late-result contract. *(Attribute.)*
10. **Trim frontmatter triggers to the formula (3.1).** Especially unity-skill-create (60-word description) and any trigger exceeding ~200 chars; re-run the YAML cap truncation warning is evidence some already get cut. *(Attributes.)*
